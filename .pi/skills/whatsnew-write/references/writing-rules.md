# 条目怎么写

日志的读者是**用这个网页客户端的人**，不是读 diff 的人。一条合格条目 = 他看完知道自己多了什么、或什么毛病没了、或以后哪条规矩变了。

## 三组，只写存在的组

| 组 | 收什么 | 例子 |
|---|---|---|
| **新增** | 新入口、新能力、原来要手工现在自动了 | 「设置里新增「子代理」页：默认模型、思考档位、并发深度都能改 #229」 |
| **修复** | 用户能撞上的毛病被修掉（不是「重构了 X」） | 「公网隧道默认走 http2，链接不再一分钟就失效、也不会报 1033 #210」 |
| **设计决定** | 有代价、用户会这么觉得的选择，通常能对上一条 D | 「工作区标签行只认一种顺序：拖动即所见，固定组与「补位」不再参与排序 D174」 |

## 什么不写

- 纯内部：重构、重命名、类型收紧、测试、CI、依赖升级、脚本调整。**一条都不写**。
- 过程：试了几版、谁审的、修了几轮。
- 自我表扬与形容词：「大幅提升」「体验更好」「更加丝滑」—— 换成它到底变了什么。
- 从代码里才看得见的东西：函数名、类名、`bridge/src/*.ts:123` 行号（**路径只能出现在「想看代码去点这里」的位置，且必须是用户能点开的仓库内路径**）。
- 假版本号：本项目没有 semver 发布会，不写 `v1.2.0`。

## 字数与形状

- 一条 15–40 字，动词开头或「哪里 + 怎么变了」。
- 每条结尾带锚点：`#PR`（已合进的 PR），或 `D<数字>`（`docs/DECISIONS.md` 的决定），两者都有就都带：`… #229 D164`。
- 一批 5–12 条最舒服。超过 15 条说明攒太久了，或者把内部改动也写进来了。

## 拿不准时的判断

1. 用户会因为这个改变自己的操作习惯吗？会 → **新增**。
2. 用户以前会撞上、现在不撞了 → **修复**。
3. 用户觉得「怎么这样」但设计上就是要这样 → **设计决定**（去 D 里找那条，带 D 号）。
4. 三条都不沾 → 不写。

## 好 / 坏

| 坏 | 好 |
|---|---|
| `fix: 修了 tunnel 的 keepalive 问题` | 「公网隧道默认走 http2，链接不再一分钟就失效 #210」 |
| `refactor: 抽出 viewer 的 pane 状态` | （不写） |
| 「优化了子代理卡片的渲染性能」 | 「后台跑的一组子代理，卡片补上任务原文、执行者、过程记录和最终输出 #208」 |
| 「更新了文档」 | （不写；除非文档本身就是用户读的入口，例如 README 的用法段变了） |
| 「新增 whatsnew 页」 | 「设置里能看本项目的更新日志了：和 pi 的那份分开放，`/whatsnew` 直达 #233」 |

## 术语

用 `GLOSSARY.md` 里的词：**会话**（不是「对话」）、**工作区**、**接管**、**派发的子代理**、**隧道**、**口令**。日志里不要发明新叫法 —— 用户界面上写的是什么，日志就跟着叫什么。
